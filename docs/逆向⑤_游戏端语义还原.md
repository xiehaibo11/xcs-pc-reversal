## 1. 启动与生命周期

### 1.1 MainApp（quesheng/controller/MainApp.java，54 行）

`main()` → `Application.launch()`（MainApp.java:50-52）。JavaFX 生命周期三个钩子：

| 钩子 | 行为 | 行号 |
|---|---|---|
| `init()` | 空操作（仅 super） | MainApp.java:24-26 |
| `start(Stage)` | 见下 | MainApp.java:28-40 |
| `stop()` | IM 登出 + SDK 释放 + `System.exit(0)` | MainApp.java:42-48 |

`start()` 的窗口预载序列（MainApp.java:29-39）：

1. `new StageController()`（:29）。
2. 依次 `loadStage("LoginView", "/quesheng/view/LoginStageView.fxml")`、`"IndexView"`←MainStageView、`"SettingView"`←SettingStageView（:30-32）。**三个窗口在进程启动时全部加载完毕**（控制器 initialize 全部执行完），但只 `show` LoginView（:39）。
3. SettingView 特殊化：`setAlwaysOnTop(true)`、`initModality(APPLICATION_MODAL)`、`resizable=false ×2`、标题"规则设置"（:33-37）。
4. `setPrimaryStage("primaryStage", primaryStage)` 把 JavaFX 主 Stage 也注册进表（:38）——此后 primaryStage 与三个 FXML 窗口同表共存，但业务代码从不 `show` 它。
5. `setStage("LoginView")`（:39）显示登录窗。

`stop()`（:42-48）：`LocalUDPDataSender.getInstance().sendLoginout()` 发 IM 登出帧（type=3），`IMClientManager.resetInitFlag()+release()`，最后 `System.exit(0)`。out_btn 的处理器（MainController.java:895-900）与之逐行相同——**正常退出路径有两条，语义一致**。

### 1.2 StageController：窗口注册表机制（StageController.java，91 行）

核心数据结构：`HashMap<String, Stage> stages`（StageController.java:28）——**名字 → Stage 实例**的全局注册表。

| 方法 | 语义 | 行号 |
|---|---|---|
| `addStage(name, stage)` | 入表 + 统一标题 `"HD" + param.version_name`（即 "HDv2.1.0"）+ 统一图标 logo.png | :30-34 |
| `getStage(name)` | 查表 | :36-38 |
| `setPrimaryStage(name, stage)` | = `addStage`（主 Stage 走同一注册路径） | :40-42 |
| `loadStage(name, fxml, styles...)` | FXMLLoader.load → Scene → new Stage → 逐个 initStyle → addStage → **`(ControlledStage)loader.getController().setStageController(this)` 反向注入** → true；异常打印"加载场景出错！"返回 false | :44-64 |
| `setStage(name)` | `getStage(name).show()` | :66-69 |


### 2.2 choseIp 的 DES 存取代码路径（首启用口令机制）

DESKit（util/DESKit.java，90 行）：
- 硬编码 key = `"nihao985"`（:14）。
- `Encrypt`: `DES/CBC/PKCS5Padding`，**IV = DESKeySpec.getKey()（即 "nihao985" 前 8 字节）**（:26-40，Cipher 串 :31，IV :32）→ 输出**大写 HEX**（byteToHexString :73-83）。
- `Decrypt`: 同参数，IV 用 keyBytes（:42-56，:48）。
- 结论：**key=IV="nihao985"，算法 DES/CBC/PKCS5Padding，密文为大写十六进制串**。解密可用 `openssl enc -d -des-cbc -K 6E6968616F393835 -iv 6E6968616F393835 -nopad?`（注意 PKCS5 去填充，须让 openssl 自己 pad——即不带 -nopad）验证。

登录窗与 choseIp 的完整状态机：
1. **读回显**（LoginController.java:124-135）：choseIp≠null → `DESKit.Decrypt` 得明文 host → **Base64(host) 显示在 ipchose 输入框**（:128-130）。即 UI 上永远显示 Base64 形态，盘上存 DES 形态。
2. **首启用**：isFirstLogin=true 或 choseIp=null → 口令行可见（:120-123 反向逻辑：仅当 isFirstLogin 显式为 false 才隐藏）。
3. **提交**（processLogin，:212-235）：
   - ipchose 空判（:215-217，"口令不能为空"）。
   - **尝试 Base64 解码输入**（:219-226）：`Base64.getDecoder().decode`，解码失败静默吞异常（empty catch :224-226）——即**用户可直接输入明文 IP，也可输入 Base64(IP)**，两种都接受。
   - `Config.systemConfig.setChoseIp(DESKit.Encrypt(serverUrl))`（:227）——**此时只写内存，不落盘**；落盘发生在登录成功后写 users 时（:195-201）或设置窗关闭时（MainController.java:843）。
   - `Config.initialize(null)`（:228）拉牌图配置（§3.2）。
   - 账密空判（:229-231）→ 进度框（:233）→ `userLogging`（:234）。
4. **:8081 拼接点**：`HttpKit.Post("http://" + DESKit.Decrypt(Config.systemConfig.getChoseIp()) + ":8081" + "/api/login/login", ...)`（:179）——**端口硬编码 8081，sconfig 里只存 host/IP**。
5. **死代码证据**：processLogin 里定义了 `port_regex`（IP:端口 正则）与 `regex`（纯 IP 正则）两个局部变量（:213-214）**全文无引用**——证明历史版本曾接受 `IP:port` 口令形态并校验，现版退化为"任意串先试 Base64 再存"。这是"不能再按 IP:8081 配方构造 sconfig"结论（逆向④ §5）的源码级实锤。

## 3. util 层语义

### 3.1 HttpKit（util/HttpKit.java，71 行）

- `Post(url, map, callback)`（:38-58）：**每次调用 new 一个 OkHttpClient**（:44-54，无连接池复用）；FormBody 逐条 add（:39-43）→ `Content-Type: application/x-www-form-urlencoded`；**内存 CookieJar**（cookieStore 按 host 存取，:36,44-54）——**注意每请求新建 client 但 cookieStore 是 static**，cookie 实际全局共享；请求头固定 `Authorization: Bearer + param.jwt`（:55）；`enqueue` 异步回调（:57）。
- `get(url, map, callback)`（:60-69）：名字叫 get，**实际发的是 HTTP PUT**（Request.Builder().put(body)，:67），且**不带 Authorization 头、不带 CookieJar**。全代码库**无任何调用方**——死方法，仅作源码瑕疵记录。

### 3.2 Config（util/Config.java，578 行）——全局静态仓库 + 洗牌器 + 牌图加载器

**静态字段**（:43-73）：
- 配置：`config_file_url="./sconfig.config"`（:43）、`logo_url`（:44）、`systemConfig`（:45，全程序唯一 SystemConfig 引用点）。
- 预载图（static 块 :539-550）：LANSE/LVSE/HONGSE（蒙色覆盖层）、GANGFANGXIANG/PENGFANGXIANG/CHIFANGXIANG（+_YUCE 变体）、GANG、FANGPAO——从 `/quesheng/view/image/` 读。
- 尺寸：SCREEN_WIDTH/HEIGHT（静态缺省 960×720，:551-552；运行时 MainController.java:400-403 按主屏覆盖）、MJ_WIDTH/HEIGHT 及 _1_2/_3_4 派生（静态缺省 62/100，:553-558；运行时公式见 §4.2）、MJ_COUNT（缺省 108，:559）。
- **牌局四大容器**（:560-565）：`weina = HashSet<Mj>(200)`（未拿/桌面牌堆）、`yina = LinkedList`（已拿/手牌）、`yuce = LinkedList`（预测牌）、`yichu = LinkedList`（已出牌池）；加 `huanhoupai_yixuan`/`jiuzhengpai_yixuan`（换手牌/纠正换牌的选中备份）。**weina 是 HashSet 而 Mj.hashCode() 恒 0**（Mj.java:217-219）——全部元素挤进同一桶，靠 equals（Mj.java:221-224，比较 serial_number/direction/mahjong_number/result/zhuo_id 五元组）判等。这是"同一张牌"的**身份定义**：五元组相同即同一张（换手牌后 serial_number 换了，equals 即不同）。
- `mjConfigs` + 私有 `mjImages`（:72-73）：牌图配置与已加载 Image，**按下标一一对应**（initialize 里同步装载）。

**getImageByNumber(number)**（:75-81）：线性查 mjConfigs 中 number 匹配项，返回对应 Image；找不到返回 null。

**getImageByMj(Mj)**（:83-92）：牌面替换语义——
- `kedi_caisheng==true` 且 `andaitipaixianshi!=1` → 显示**原牌面 yuanpai**（被"代替财神牌"吞掉的牌，显示真身；:85）；
- `kedi_huapai==true` 且（zixuanhuapai==1 或 leqing==1）→ 显示 yuanpai（被当花牌的牌显示真身；:86）；
- 其余显示 result。即 **result 是"当前语义面"，yuanpai 是"物理面"**，双字段实现"牌可被改写语义但可回显原样"。

**xipai(zhangshu, fangshu) / xipai(zhangshu)**（:94-157 / :159-457）——本地测试发牌器（无服务器参与）：
1. 造牌：`mjConfigs` 前 27 项（万1-9=1..9、条=11..19、筒=21..29）每种 4 张（90 张模式 5 张，:165-168），34 段之后为字牌(31-37)、花牌(41-48)区间按余量补足；`serial_number` 统一 123456（:103 等）；`Collections.shuffle` 洗散（:131/:200）。
2. 特例改写：112 张模式把 result==31 全改 35（:201-206）——字牌"红中"变"发财"类的地方规则（推断：对应某种 112 张牌型的字牌替换）。
3. 分堆：按 MJ_COUNT 把 zongpai 依序切成 2/3/4 家、按 mahjong_number 0..n 编号、direction 赋 0/1/2/3（各分支 :207-456）。**136 张按 mapaicengshu 分两种切法**（两层各 34 张 :331-362；三层 33/36/33/34 :363-393）——这正是"136 三层码牌每家牌数不等"的实现。

### A.4 三个最有价值的语义洞察（审计视角摘要）

1. **单向数据流 + 本地状态机**：游戏端对服务器**只拉不推**（唯一上行是登录/激活/OTA/改密 4 个元数据端点，牌局数据仅有 `/api/yiZhuo/get` 读）。摸/出/碰/杠/吃/胡全是**本地模拟状态机**（Config.weina/yina/yuce/yichu + paizhuantai），服务器推送（typeu=1）只触发"重新拉一次 + 告警闪烁"，不直接驱动 UI。这决定了 fixture 服务器的最小实现面：2 个 GET 语义端点 + 1 个 IM 推送即可让全部 UI 跑起来。
2. **"坐标即语义"的牌墙编码**：`mahjong_number` 的奇偶/模 3 是码牌层位（两层/三层），`direction` 0-3 是方位；过张/过栋/栋半/对调四组操作全部是对这两个整数的算术重排，`result`（含 >40 花牌、52-58 广西百搭、35 乐清花牌改写、yuanpai 双面）是"语义面"。一张牌的完整身份=五元组 equals + 语义双字段（result/yuanpai）+ 三归属字段（napai/yuce/chupai_direction）——理解这套编码即可推演任何 UI 操作的落点。
3. **Robot 物理光标 = 人的替身**：每次出现可吃/可碰/可杠/可胡/摸牌机会或 AI 推荐（chupai:6389-6397,6598-6604,6695-6701；displayYinaPai:7701-7710），程序把 **OS 级鼠标光标**移到目标图标/牌上——配合 JIntellitype 全局热键"模拟 fireEvent"，整个客户端的设计目标是**替真人完成看牌-决策-指点**的辅助链路（配合登录窗"魔术道具,请勿用作其它用途"文案，LoginStageView.fxml:67）。安全审计意义上：敏感面=DES 硬编码密钥+明文密码表单+无验证码登录+激活无凭据字段。
