# A2 核对报告：VerifyPwdWindow 校验口令通过后的解锁范围（逐行闭环）

> 核对对象：原始反编译源码 `analysis/xcs-cs/`（xcs.exe 2.0.15，ILSpy 产物）
> vs 还原可编译工程 `analysis/xcs-cs112/`。
> 核对方式：逐文件 diff + 过滤生成代码噪声（InitializeComponent / Connect / _contentLoaded /
> DebuggerNonUserCode / GeneratedCode / EditorBrowsable / IL_* 注释）后比对业务逻辑。
> 全程仅静态分析，未运行任何 exe。

---

## 一、结论（回答路线图遗留问题）

**"校验口令通过后的解锁范围" = `Global.verify` 是一个进程级单布尔（static，初始 false），
全工程唯一读点是 `MainWindow` 构造函数，唯一写 `true` 的点是 `ErrorWindow.Window_PreviewTextInput`。
解锁后（同一进程内）不存在任何逐功能权限控制。**

- **ErrorWindow 是真正的授权门**：每次进程启动 `verify=false`，StartupUri 指向的 MainWindow
  构造时发现 `!verify` 就把自己关掉、弹 ErrorWindow；只有全窗口键盘累积输入的 MD5 命中
  口令才会 `verify=true` 并放行。
- **VerifyPwdWindow 只是"首次设置专属密钥"界面**（以及从联机配置弹窗进入的"重置密钥"界面），
  它到达时 `verify` 必然已经是 true，它本身不做任何解锁，只负责把新密钥 MD5 写回 INI。
- 该判断被代码证据**确认**（原任务预测成立），读写点全集见下文第四节。

### 2.3 关键语义点（逐行确认）

1. **toLogin 语义**（`VerifyPwdWindow.cs:17` `public bool toLogin = true;`）：
   默认 true —— 从 ErrorWindow 首设密钥链路进来时，`_save` 写完 INI 后直接
   `new MainWindow().Show()` 进入登录页（`:64-67`）。唯一显式置 false 的入口是
   `OnlineWindows.ResetVerifyPwd_Click`（还原版 `OnlineWindows.xaml.cs:40-46`），
   用于"已解锁状态下重置密钥"，写完 INI 后只 `Close()` 不再跳转。原版与还原版完全一致。
2. **口令写 INI 时机**：`_save` 中在 `toLogin` 判断**之前**无条件写 INI（`VerifyPwdWindow.cs:63`）——
   即使用户从"重置密钥"进入（toLogin=false），新密钥也会立即生效（下次启动 ErrorWindow
   用新口令校验）。原版与还原版一致。
3. **解锁后窗口跳转**：ErrorWindow 命中后按 `isSetPwd` 二选一进 MainWindow 或 VerifyPwdWindow
   并 `Close()` 自己（`ErrorWindow.cs:55-63`）。VerifyPwdWindow 成功后进 MainWindow（toLogin=true
   时）并 `Close()`。均为无模态 `Show()`。原版与还原版一致。
4. **输入累积无回退**：ErrorWindow 的 `inputText` 只在 `PreviewTextInput` 里追加
   （`ErrorWindow.cs:49-65`），`TextBox_KeyUp` 仅 `Console.WriteLine(e.Key)`（`:43-47`）——
   没有退格/清空逻辑，跑 MD5 的是"自窗口打开以来全部键入字符的累积串"。
   VerifyPwdWindow 的 `pwdInput_KeyUp` 以 `(int)e.Key == 6`（Enter 键）触发 `_save`
   （`VerifyPwdWindow.cs:37-45`）。原版与还原版一致。
5. **EditPwdWindow 与 verify 无关**：它改的是服务器账号密码（`EditPwdViewModel.SaveEditPwd`），
   成功后 `Application.Current.MainWindow.Close(); new MainWindow().Show()`（`EditPwdWindow.cs:34-39`），
   此时 verify 已为 true，不触发授权门。勿与 VERIFY/PWD 混淆。

## 四、启动入口核对

**原版**（`analysis/xcs-cs/distinguish/App.cs`）：
- `Main()`（:63-71）：`new App(); app.InitializeComponent(); app.Run();`
- `InitializeComponent()`（:52-61）：**先** `StartupUri = new Uri("LoginWindow.xaml")` **再** LoadComponent app.xaml。
- `OnStartup` override（:15-19）：`base.OnStartup(e); AppDomain.CurrentDomain.AssemblyResolve += OnResolveAssembly;`
  （OnResolveAssembly :21-48 从 manifest 资源加载嵌入 DLL，服务单文件发布形态）。
- `loginwindow.baml` 的 x:Class = `distinguish.MainWindow`（`baml-strings/loginwindow.strings.txt:5`）——
  即 **StartupUri "LoginWindow.xaml" 实际实例化的是 MainWindow 类（登录界面）**。

**还原版**（`analysis/xcs-cs112`）：
- `App.xaml:2`：`StartupUri="LoginWindow.xaml"`（由构建生成的 `obj/.../distinguish/App.g.cs:57` 写入）。
- csproj 用 `LogicalName` 复刻原始资源名：`<Page Include="distinguish/MainWindow.xaml" LogicalName="loginwindow.xaml" />`，
  且 `MainWindow.xaml:2` `x:Class="distinguish.MainWindow"` → pack URI `LoginWindow.xaml` 解析到同一资源名，
  **启动首窗 = MainWindow（登录界面），与原版等价**。
- `App.xaml.cs` 原状：`internal void DoStartup(StartupEventArgs e)` 调 `OnStartup(e)` 并挂
  AssemblyResolve——这是反编译残片（原版 OnStartup 的影子），**全工程 grep 无调用点**；
  真正 WPF 生命周期走 `App.g.cs` 生成的 `Main()`，因此还原版缺 AssemblyResolve 挂钩
  （对还原构建无实际影响：依赖 DLL 经 HintPath 引用拷贝到输出目录正常加载；
  但与原版行为不等价，属实质偏差，已修复，见第五节）。

## 五、发现的实质差异与修复

### 5.1 实质行为差异（已修复）

| 差异 | 原版行为 | 还原版修复前行为 | 影响 | 修复 |
|---|---|---|---|---|
| `App.OnStartup` 未被 override，`DoStartup` 为死代码 | 启动即挂 `AssemblyResolve`，嵌入资源 DLL 加载失败时有兜底 | 钩子永不安装（DoStartup 无人调用） | 对 HintPath 引用的常规构建无功能影响，但与原版**不等价**，且若复刻单文件发布形态会直接崩溃 | `App.xaml.cs` 删除 `DoStartup`，改为 `protected override void OnStartup(StartupEventArgs e) { base.OnStartup(e); AppDomain.CurrentDomain.AssemblyResolve += OnResolveAssembly; }`，与原版 App.cs:15-19 逐行对齐 |

### 5.2 非实质（噪声/等价写法），未改动

- `partial class`、XAML 生成字段与事件接线、`((Window)this)`/`((Application)this)` 显式转换、
  delegate→lambda、IL_* 注释、`AssemblyInfo.cs` 中 `ThemeInfo` 注释形式差异。
- 解锁链路本身（ErrorWindow / VerifyPwdWindow / MainWindow）**原版与还原版逐行一致，无实质偏差**。

## 六、复核结论

- A2 遗留问题闭环：**解锁范围 = 仅 MainWindow 入口守卫**（进程级单布尔 `Global.verify`），
  ErrorWindow 为真授权门（每次进程启动必经），VerifyPwdWindow 仅为首设/重置密钥界面，
  解锁后无逐功能权限控制——预测结论经代码证据确认。
- 还原工程 `analysis/xcs-cs112` 与原始反编译源码在解锁链路上无实质行为偏差；
  唯一实质偏差（App.OnStartup/AssemblyResolve 死代码残留）已修复并构建通过。
