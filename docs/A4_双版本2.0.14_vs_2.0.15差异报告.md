## 一、① 真实业务差异（共 8 条）

### B0. 版本常量升级：`app_version` 2.0.14 → 2.0.15

- 证据：`analysis/distinguish-cs112/distinguish.Common/Global.cs:33` `app_version = "2.0.14"`
  vs `analysis/xcs-cs112/distinguish.Common/Global.cs:33` `app_version = "2.0.15"`。
  原始层同位置（`distinguish-cs/distinguish.Common/Global.cs:33` / `xcs-cs/...:33`）一致。
- 影响行为：`checkAppVersion()`（`xcs-cs112/distinguish.ViewModel/HomeViewModel.cs:3368`）
  用它向服务器上报/比对版本 → 走 `app/check_update` OTA 判定；两版程序集版本号
  （AssemblyVersion）都是 2.0.1.0，仅此运行时常量不同。
- 注意：两版 `Global.app_name` 均为 `"xcs"`（`Global.cs:35`），多品牌开关值未变。

### B1. Model 新增 `Channel.DeleteOffset` 字段（2.0.15 全部新逻辑的数据基础）

- 证据：`analysis/xcs-cs112/distinguish.Model/Channel.cs:36`（字段 `private int deleteOffset;`）
  与 `:215-226`（属性 `DeleteOffset` 的 getter/setter）。2.0.14 版本整个文件**无** deleteOffset
  （`analysis/distinguish-cs112/distinguish.Model/Channel.cs` grep 0 命中）。

- 语义：记录该通道已"删牌前移"的次数（逻辑位偏移量），供 101 消息重映射（B3）、
  msg114 收满复位（B5）、SendData 成功复位（B6）使用。

### B2. UI 文案参数化：硬编码按钮文案 → ViewModel 绑定 + `initText()` 按 `app_name=="xcs"` 切短文案

  2.0.14 永远显示长文案。非 xcs 品牌构建（同代码、app_name 不同）回退长文案。

### B3. 101 消息（WS 图牌数据）按 `DeleteOffset` 重映射 + 越界丢弃；计数/自动发送块移入 else 分支

- 2.0.14：直接用原编号计算槽位 `int index = protocolDataContentImg.mahjong_number / 2;`
  （`analysis/distinguish-cs112/distinguish.ViewModel/HomeViewModel.cs:1991`），无任何越界保护。
- 2.0.15：`analysis/xcs-cs112/distinguish.ViewModel/HomeViewModel.cs:2133`
  `int num = protocolDataContentImg.mahjong_number - channel.DeleteOffset;`，
  `:2134-2139` 若 `num <= 0 || num > channel.Mj_count` 则打印
  `"丢弃越界WS消息: original=…, offset=…, effective=…"` 并跳过该消息（新日志输出）；
  命中范围内才以 `num` 走原 bottom(偶)/top(奇) 槽位计算（`:2141` 起，逻辑与 2.0.14 相同，仅变量换名）。
- 结构变化：2.0.14 中"统计已识别张数 → 收满则自动 `SendData(autoSend:true)`（:2155-2156）、
  否则 `PlayReceiveSound()`（:2172）"的整块代码在每条 101 消息后无条件执行；
  2.0.15 将该块移入"未越界"else 分支内（`:2234-2322`，`SendData(autoSend:true)` 在 `:2303`、
  `PlayReceiveSound()` 在 `:2319`）——越界消息不再参与计数与收满判定。
- 行为影响：2.0.15 在"删过牌"的通道上，服务器发来的编号比界面上当前逻辑位靠后
  （因为删除后界面整体前移），按 DeleteOffset 平移后仍能落回正确槽位；
  越界消息（通常是删牌后重发/乱序的旧编号）被安全丢弃，避免 2.0.14 中会发生的
  越界索引与画面错位。这是"删牌重排"机制（B4）的接收端配套。

### B4. RemoveItem 删牌语义重写：单格清空 → 删除并整体前移（ShiftForward）

- 2.0.14（`analysis/distinguish-cs112/distinguish.ViewModel/HomeViewModel.cs:3124-3132`）：
  仅清空当前选中格的三项显示字段（`ResultImg/UploadImg/Result`），槽位本身保留（空洞）。
- 2.0.15（`analysis/xcs-cs112/distinguish.ViewModel/HomeViewModel.cs:3328-3366`）：
  1. 解析 `selectChannelMjResult.Index`（格式 `方向:top|bottom:序号`，`:3334-3344`）；
  2. 换算逻辑位 `num = top ? result*2 : result*2+1`（`:3345`）；
  3. `FindChannelByIndexPrefix` 按方向前缀找通道（`:3346`，实现在 `:2370-2377`）；
  4. `ShiftForward(channel, num)`（`:3355`，实现在 `:2360-2368`）：把删除位之后的全部槽位
     逐个前移（经 `CopyMjSlot` `:2348-2358` 复制 8 个字段），末槽 `CleanMjItem`；
     槽位→top/bottom 的映射由 `GetLogicalSlot` `:2338-2346` 完成；
  5. `channel.DeleteOffset++`（`:3356`）；
  6. 若 `upSend` 则立即 `setUpMjData()` 刷新上牌视图（`:3357-3360`）、
     校验页可见时 `clacValidPageData()`（`:3361-3364`）。
- 行为影响：2.0.15 删除一张牌后，其后所有牌整体前移补位（界面上不留空格，
  逻辑编号连续），并用 DeleteOffset 记住"前移了几张"，与 B3 的重映射、B5/B6 的复位配合。
  2.0.14 只能挖空，之后收到的牌仍按原编号落位，空洞永远留在中间。

### B5. msg114（收到服务器"收满/结束"通知）全部通道 `DeleteOffset` 归零

## 六、行为影响总述

2.0.15 的核心演进是**"删牌重排"闭环**：用户在校验页删掉一张牌（B4）→ 该通道 DeleteOffset+1、
后续牌前移补位 → 服务器随后下发的 101 编号消息按 DeleteOffset 平移落位、越界安全丢弃（B3）→
一轮收满（B5）或发送成功（B6）时偏移复位，回到初始状态。辅以免校验发送开关（B6），
并把整套 UI 文案参数化以支持 xcs 短文案品牌（B2），清牌时机对齐服务器消息流（B7）。
2.0.14 则只能挖空牌位、强制校验发送、固定长文案。
